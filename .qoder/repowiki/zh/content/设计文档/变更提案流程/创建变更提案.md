## 变更提案的触发条件
当以下情况发生时，必须创建变更提案：

- **新增功能或能力**：如添加缓存、自动重载、新路由策略等。
- **架构或模式变更**：如引入新的依赖（Redis）、修改运行时模型、重构模块结构。
- **破坏性变更**：API 接口、配置结构、数据格式的不兼容更改。
- **性能优化**：涉及行为改变的性能改进，如引入负载均衡算法、响应缓存。
- **安全模式更新**：认证机制、访问控制策略的变更。
- **可观测性增强**：新增指标、日志结构变更、调试接口。

这些变更影响系统的核心行为或长期维护性，需通过提案进行评审和共识。

## 豁免提案的情况
以下类型的变更**无需**创建提案，可直接提交：

- **Bug 修复**：修复偏离预期行为的缺陷，恢复原有功能。
- **格式调整**：代码格式化、缩进修正、空白字符调整。
- **注释修改**：更新或补充代码注释、文档说明。
- **非破坏性依赖更新**：升级库版本且不改变接口或行为。
- **配置变更**：仅修改配置值而不影响结构或逻辑。
- **现有行为的测试补充**：为已有功能添加单元或集成测试。

此类变更属于维护性工作，风险低且范围明确。

## 决策树：是否需要创建变更提案
使用以下决策流程判断是否需要发起提案：

```
新请求？
├─ 是否为修复 Bug 并恢复规范行为？ → 直接修复
├─ 是否为拼写、格式或注释调整？ → 直接修复  
├─ 是否为新增功能或能力？ → 创建提案
├─ 是否为破坏性变更？ → 创建提案
├─ 是否为架构或模式变更？ → 创建提案
└─ 是否不明确？ → 创建提案（更安全的选择）
```

若存在任何不确定性，建议创建提案以确保变更经过充分评审。

## change-id 的命名规范
`change-id` 是变更提案的唯一标识，必须遵循以下规则：

- **格式**：使用 kebab-case（短横线分隔），全小写。
- **前缀**：以动词开头，如 `add-`、`update-`、`remove-`、`refactor-`。
- **唯一性**：确保在整个 `openspec/changes/` 目录下无重复。
- **描述性**：简洁明了地表达变更意图，例如 `add-cache-auto-reload-metrics`。

示例：
- ✅ `add-v0-1-basic-routing-lb`
- ✅ `add-cache-auto-reload-metrics`
- ✅ `update-health-check-strategy`
- ❌ `AddCacheFeature`（不符合 kebab-case）
- ❌ `feature/cache`（包含斜杠）

若名称已被占用，可追加 `-2`、`-3` 等序号。

## 提案文件结构搭建
创建变更提案时，需在 `openspec/changes/<change-id>/` 目录下搭建以下文件结构：

```
openspec/changes/<change-id>/
├── proposal.md        # 提案说明：Why/What/Impact
├── tasks.md           # 实施检查清单
├── design.md          # 技术设计文档（可选）
└── specs/
    └── <capability>/
        └── spec.md    # 规范增量（delta）
```

其中：
- `specs/` 下按受影响的能力（capability）组织多个 `spec.md` 文件。
- `design.md` 仅在满足特定条件时创建（见下文）。

## proposal.md 的三段式结构
`proposal.md` 采用三段式结构，清晰传达变更意图：

### Why（为什么）
用 1-2 句话说明问题背景或机会。例如：
> “网关需要响应缓存、自动配置重载和更细粒度的指标，以减少上游负载、简化运维并提升可见性。”

### What Changes（变更内容）
列出具体变更项，使用项目符号。对破坏性变更标注 **BREAKING**。例如：
- 添加响应缓存支持（GET 请求 200 响应）
- 添加基于文件哈希的自动配置重载
- 扩展 Prometheus 指标以包含缓存命中/未命中计数

### Impact（影响范围）
明确指出受影响的部分：
- **受影响的规范**：列出涉及的能力，如 `gateway-cache`, `gateway-reload`
- **受影响的代码**：关键文件或系统，如 `config schema`, `proxy handler`, `metrics`

该结构确保提案简洁且信息完整。

## spec delta 编写规范
`spec.md` 文件位于 `specs/<capability>/` 下，描述规范的增量变更，必须使用以下标题格式：

```markdown
## ADDED Requirements
### Requirement: 新功能
系统 SHALL 提供...

#### Scenario: 成功场景
- **WHEN** 用户执行操作
- **THEN** 预期结果

## MODIFIED Requirements
### Requirement: 现有功能
[完整的修改后需求]

## REMOVED Requirements
### Requirement: 已废弃功能
**Reason**: 为何移除  
**Migration**: 如何迁移
```

### 关键要求：
- 每个需求必须至少包含一个 `#### Scenario:`。
- 场景标题必须使用四级标题（`####`），不可用粗体或列表。
- 使用 `SHALL` 或 `MUST` 表示强制性要求，避免模糊措辞。
- 修改现有需求时，应复制原需求全文并修改，确保归档时保留完整上下文。

## tasks.md 的作用与实施清单
`tasks.md` 作为实施阶段的检查清单，指导开发者逐步完成工作。其结构为有序任务列表：

```markdown
## 1. 实现
- [ ] 1.1 定义配置模式
- [ ] 1.2 实现配置加载与验证
- [ ] 1.3 构建运行时快照结构
...
```

每项任务完成后勾选 `[x]`。该文件确保所有步骤被跟踪和完成，防止遗漏。在实施前应先阅读 `proposal.md` 和 `design.md`（如存在），再按 `tasks.md` 顺序执行。

## design.md 的创建条件
`design.md` 是可选文件，仅在满足以下任一条件时创建：

- **跨模块变更**：影响多个服务或模块的架构调整。
- **引入新外部依赖**：如新增 Redis、数据库等。
- **重大数据模型变更**：影响持久化结构或通信协议。
- **安全、性能或迁移复杂性高**：涉及风险评估与权衡。
- **存在技术决策歧义**：需提前明确方案以避免返工。

其内容应包括背景、目标/非目标、技术决策、风险与权衡、迁移计划和开放问题。

## 实际示例分析：add-v0-1-basic-routing-lb
以 `add-v0-1-basic-routing-lb` 提案为例：

- **change-id**: `add-v0-1-basic-routing-lb`（符合动词前缀 + 描述性命名）
- **proposal.md**: 明确说明需建立支持路由、负载均衡和可用性的 v0.1 网关基线。
- **tasks.md**: 包含 12 项实现任务、7 项测试任务和 3 项文档任务，全面覆盖实施路径。
- **specs/**: 影响 `gateway-routing`, `gateway-auth`, `gateway-availability` 等多个能力，每个均有独立 `spec.md`。
- **spec delta**: 使用 `## ADDED Requirements` 添加新需求，如前缀路由、健康检查、被动驱逐等，每个需求均配有 `#### Scenario:`。

此提案结构完整，是创建新功能的典范。

## 常见错误与排查方法
### 常见错误
1. **“Change must have at least one delta”**
   - 原因：缺少 `specs/` 目录或 `spec.md` 文件。
   - 解决：确认 `specs/<capability>/spec.md` 存在且包含 `## ADDED|MODIFIED|REMOVED Requirements`。

2. **“Requirement must have at least one scenario”**
   - 原因：场景格式错误。
   - 错误写法：`- **Scenario: 登录成功**` 或 `### Scenario: 登录`
   - 正确写法：`#### Scenario: 用户登录成功`

3. **静默解析失败**
   - 原因：场景标题格式不精确。
   - 调试：使用 `openspec show [change] --json --deltas-only` 查看解析结果。

### 验证建议
始终使用严格模式验证：
```bash
openspec validate <change-id> --strict
```
并在提交前运行 `openspec list` 和 `openspec spec list --long` 检查上下文。
