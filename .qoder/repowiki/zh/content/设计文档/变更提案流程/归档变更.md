## 引言
在 RSSHub-Gateway 项目中，变更管理遵循 OpenSpec 指南中定义的三阶段工作流程。第三阶段——变更归档，是确保项目历史记录完整性和维护活跃变更列表简洁性的关键步骤。本文档详细说明了如何在变更成功部署后，通过创建独立的 PR 将已完成的变更从 `openspec/changes/[name]/` 移动到 `openspec/changes/archive/YYYY-MM-DD-[name]/` 目录下。

## 归档流程概述
变更归档阶段在变更成功部署到生产环境后启动。此阶段的核心任务是将变更从“待办”状态正式标记为“已完成”，并将其从活跃变更目录移动到归档目录。

归档流程包括以下关键步骤：
1. 创建一个独立的 Pull Request (PR)
2. 将变更目录从 `openspec/changes/[name]/` 重命名为 `openspec/changes/archive/YYYY-MM-DD-[name]/`
3. 如果变更引入了新的能力或修改了现有能力，更新主规格文件 (`specs/`)
4. 使用 `openspec archive [change]` 命令执行归档操作
5. 在归档前运行 `openspec validate --strict` 确保变更符合所有验证规则

此流程确保了变更的历史可追溯性，并防止活跃变更列表变得臃肿。

## 归档操作的重要性
归档操作对于维护项目的健康和可维护性至关重要，主要体现在以下两个方面：

**维护项目历史记录**：归档目录 (`openspec/changes/archive/`) 充当了项目演进的完整历史档案。每个归档的变更都包含了其提案、任务清单和规格变更，为未来的开发者提供了宝贵的上下文信息。例如，`add-v0-1-basic-routing-lb` 变更的提案文件详细记录了实现基本路由和负载均衡功能的动机和影响范围。

**保持活跃变更列表简洁**：通过将已完成的变更移出 `openspec/changes/` 目录，团队可以清晰地看到当前正在进行的工作。这减少了认知负担，避免了混淆，并确保团队的注意力集中在当前的开发任务上。一个干净的活跃变更列表是高效协作的基础。

## 主规格文件更新
当一个变更引入了新的能力或修改了现有能力时，必须相应地更新主规格文件 (`specs/`)。主规格文件代表了系统当前的真实状态，是所有开发工作的“唯一真相来源”。

更新过程涉及将变更提案中的规格增量（deltas）合并到主规格文件中。例如，`add-short-subscriptions` 变更在 `specs/gateway-short/spec.md` 中添加了新的需求，这些需求在归档时需要被整合到主文件中。这个过程确保了规格文档始终与代码实现保持同步。

## openspec archive 命令使用
`openspec archive` 命令是执行归档操作的核心工具。它简化了归档流程，并确保了操作的一致性。

基本用法如下：
```bash
openspec archive [change-id]
```

该命令接受以下常用标志：
- `--skip-specs`：用于仅涉及工具或内部结构的变更，归档时跳过主规格文件的更新。
- `--yes` 或 `-y`：跳过确认提示，适用于非交互式或自动化环境。

例如，对于一个仅更新了内部脚本的变更，可以使用：
```bash
openspec archive update-internal-script --skip-specs --yes
```

## 验证要求
在执行归档操作之前，**必须**运行 `openspec validate --strict` 命令。这是一个强制性的质量保证步骤。

`--strict` 标志会执行全面的验证检查，包括：
- 检查规格文件格式是否正确
- 验证所有需求都有至少一个场景
- 确保变更的结构符合 OpenSpec 规范

此步骤确保只有完全符合项目标准的变更才能被归档，从而维护了整个规格系统的完整性和可靠性。忽略此步骤可能导致归档的变更存在缺陷，影响未来的开发工作。

## 自动化脚本示例
为了简化归档流程并减少人为错误，可以创建自动化脚本。以下是一个示例 Bash 脚本，它封装了归档的典型步骤：

```bash
#!/bin/bash
CHANGE_ID="add-new-feature"

# 1. 验证变更
echo "正在验证变更..."
openspec validate $CHANGE_ID --strict
if [ $? -ne 0 ]; then
    echo "验证失败！请先解决所有问题。"
    exit 1
fi

# 2. 执行归档
echo "正在归档变更..."
openspec archive $CHANGE_ID --yes

# 3. 提交更改
git add .
git commit -m "归档变更: $CHANGE_ID"
git push origin archive-$CHANGE_ID

echo "归档流程完成。请创建 PR。"
```

此脚本首先进行严格验证，然后自动执行归档命令，最后提交更改。团队可以根据具体需求调整此脚本。

## 常见问题与解决方案
在归档过程中可能会遇到一些常见问题，以下是解决方案：

**归档冲突**：如果两个变更同时被归档并修改了同一个文件，可能会发生 Git 冲突。解决方案是，在创建归档 PR 前，先将主分支的最新更改合并到你的分支中 (`git pull origin main`)，然后手动解决任何冲突。

**验证失败**：如果 `openspec validate --strict` 失败，应根据错误信息进行修复。常见原因包括格式错误的场景标题或缺失的场景。使用 `openspec show [change] --json --deltas-only` 命令可以帮助调试和检查增量解析结果。

## 结论
变更归档是 OpenSpec 工作流程中不可或缺的最后一步。通过遵循本文档中描述的流程——创建独立 PR、移动变更目录、更新主规格、使用 `openspec archive` 命令并执行严格验证——团队可以确保项目历史记录的完整性和可追溯性。这一实践不仅维护了 `specs/` 目录作为系统当前状态的权威来源，也保持了 `changes/` 目录的清晰和专注，从而支持了项目的长期健康和可持续发展。
